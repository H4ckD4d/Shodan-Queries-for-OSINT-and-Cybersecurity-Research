# Developers and Community

> **Original creator, project owner, and primary maintainer: Chris Cruz | h4ckd4d**

**h4ckd4d Internet Exposure Query Atlas** welcomes developers, OSINT researchers, EASM practitioners, security engineers, technical writers, data-model designers, and maintainers of Internet-intelligence tooling.

## Where contributors can help

High-value contribution areas include:

- validating platform syntax against official documentation;
- documenting semantic differences between vendors;
- adding defensive query intents;
- building schemas and static validation tooling;
- creating documentation-safe examples;
- improving adapters, tests, CI, and analyst documentation;
- reviewing false-positive and asset-attribution risks;
- improving portability across Internet-exposure data sources;
- designing normalization and evidence-confidence models.

## Contribution workflow

1. Open or select an issue describing a query-intent gap, vendor-semantic correction, documentation improvement, or engineering proposal.
2. Create a focused branch or fork.
3. Use the standards in `docs/query-standard.md`.
4. Keep all examples restricted to documentation-safe or explicitly authorized scope.
5. Add or update machine-readable catalog entries when applicable.
6. Run repository validation locally.
7. Open a pull request explaining the objective, vendor semantics, source documentation, limitations, and validation performed.

## Professional review criteria

Pull requests are reviewed for:

- defensive value;
- technical correctness;
- primary-source validation;
- clear vendor semantics;
- scope and authorization controls;
- reproducibility;
- safe examples;
- analyst usability;
- maintainability.

## Contributor credit

Accepted contributors retain credit through Git history, pull requests, release notes, and acknowledgments where appropriate. **Original project authorship, ownership, and primary maintenance remain attributed to Chris Cruz | h4ckd4d.**

## Collaboration principles

Be precise, respectful, evidence-driven, and transparent about limitations. Do not include credentials, personal data, sensitive third-party infrastructure, or examples intended to facilitate unauthorized access.

**Developers are invited to propose adapters, schemas, query intents, CI improvements, documentation, and defensive research workflows through GitHub Issues and Pull Requests.**
